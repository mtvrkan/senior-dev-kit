## REST CONVENTIONS

### Resource naming

- Nouns, plural, lowercase, hyphen-separated: `/users` `/blog-posts` `/order-items`
- Nested resources (max 2 levels): `/users/{id}/orders` `/orders/{id}/items`
- Actions that don't fit CRUD: POST to verb endpoint `/orders/{id}/cancel` `/sessions/refresh`
- Never verbs in resource names: ~~`/getUsers`~~ ~~`/createPost`~~

### HTTP methods

| Operation | Method | Status |
| --- | --- | --- |
| List | GET /resources | 200 |
| Get one | GET /resources/{id} | 200 or 404 |
| Create | POST /resources | 201 + Location header |
| Full update | PUT /resources/{id} | 200 |
| Partial update | PATCH /resources/{id} | 200 |
| Delete | DELETE /resources/{id} | 204 (no body) |
| Non-CRUD action | POST /resources/{id}/action | 200 |

### Error response format — RFC 9457

Default for a NEW project/service with no established error shape yet:

```json
{
  "type": "https://api.example.com/errors/not-found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "User with id 'abc123' was not found",
  "instance": "/users/abc123"
}
Content-Type: application/problem+json
```

Never: status 200 with `{ success: false }` body · HTML error pages for APIs.

**Existing project with an established error shape** (e.g. a framework preset's idiomatic
default like NestJS `HttpException`, FastAPI `{"detail": ...}`, Django REST `{"error": ...}`):
match the existing shape — per `001-conventions.md`'s RULE PRECEDENCE, the project's own
convention (and a framework preset's idiomatic default) wins over this generic recommendation.
"Never plain string errors" still applies regardless of which shape is in use — every error
response must be structured JSON, not a bare string.

## OPENAPI 3.2 — SCHEMA-FIRST WORKFLOW

1. Define schema in `openapi.yaml` / `openapi.json` BEFORE implementation
2. Generate types from schema: `openapi-typescript openapi.yaml -o types/api.d.ts`
3. Validate requests/responses against schema at runtime (zod, typebox, ajv)
4. Keep schema as single source of truth — no manual type drift

Every endpoint must have: summary · operationId · request body schema · all response schemas (2xx + 4xx + 5xx)

## AUTH REQUIREMENTS

Every protected endpoint MUST:

- Verify token/session before any business logic
- Check ownership (IDOR): `resource.userId === req.user.id`
- Return 401 (unauthenticated) or 403 (unauthorized) — never 404 to hide existence
- Never expose user A's data based on user B's request

Auth checklist:

- JWT: `alg` not `none` · expiry set (`exp`) · sensitive data NOT in payload
- Session: `httpOnly` + `secure` + `sameSite=Strict` cookie
- CSRF: SameSite+Origin check or CSRF token for mutating endpoints
- Rate limiting: MUST exist on login, register, password-reset, OTP endpoints

Full JWT/session/CSRF implementation patterns (refresh rotation, cookie options, origin
checks): `agent_docs/security-protocols.md` § AUTHENTICATION PATTERNS — this checklist is the
summary, that file is canonical for the code shapes.

## RATE LIMITING

Every public endpoint: rate limit. Auth endpoints: strict rate limit.
Headers: `X-RateLimit-Limit` · `X-RateLimit-Remaining` · `X-RateLimit-Reset`
Response on exceed: `429 Too Many Requests` with `Retry-After` header
Per-endpoint window/max values by sensitivity: `agent_docs/security-protocols.md`
§ RATE LIMITING STRATEGY (canonical for the numbers — don't restate them here).

## INPUT VALIDATION — at system boundary only

Validate ALL user input at the API boundary (controller/handler layer).
Never trust: query params · path params · request body · headers · cookies
Use: Zod (TS) · Pydantic v2 (Python) · `binding:"required"` (Go) · Bean Validation (Java)
Never pass raw `req.body` or `$_POST` to DB queries, shell commands, or template engines.

## CORS

Production: NEVER `Access-Control-Allow-Origin: *` for credentialed requests
Allowlist specific origins: `['https://app.example.com', 'https://admin.example.com']`
Credentials (`withCredentials: true`): require explicit origin, never wildcard

## API VERSIONING

Prefer URL versioning: `/v1/users` `/v2/users`
Breaking change = new major version (v1 → v2)
Non-breaking additions: add fields (never remove), new optional params
Deprecation: add `Deprecation` header + `Sunset` date + migration guide in docs
Keep v1 running for minimum 6 months after v2 launch

Breaking changes checklist:

- [ ] Removed field from response
- [ ] Required field added to request
- [ ] Field renamed
- [ ] Status code changed
- [ ] Error format changed
- [ ] Auth requirement changed

Code templates for the transition (parallel v1/v2 routing, Deprecation/Sunset middleware with
RFC 9745 HTTP-dates, migration doc skeleton): `agent_docs/api-versioning-guide.md`.

## PAGINATION

Cursor-based (preferred for large/real-time data):

```json
{ "data": [...], "cursor": "eyJpZCI6MTIzfQ==", "hasMore": true }
```

Offset-based (acceptable for small, stable data):

```json
{ "data": [...], "total": 100, "page": 1, "perPage": 20 }
```

Never: return unbounded lists without pagination.

## IDEMPOTENCY

POST/PATCH mutations: support `Idempotency-Key` header for safe retry.
Store key → response mapping for 24h. Return cached response on duplicate key.

## WEBHOOK SECURITY

Sign webhook payloads with HMAC-SHA256.
Include `X-Webhook-Signature: sha256={hex}` header.
Receiver verifies signature before processing. Never trust payload without verification.
Reject payloads >5 minutes old (timestamp in payload).

## SENSITIVE DATA

Never in URL params: passwords · tokens · API keys · PII (URLs are logged)
Never in response: password hashes · internal IDs used for enumeration · stack traces
Redact in logs: Authorization header · Cookie header · request body password fields

## PERFORMANCE BUDGETS

## API PATTERN SELECTION

| Context | Pattern |
| --- | --- |
| Full-stack TS monorepo, same team | tRPC |
| Public API or multi-client | REST + OpenAPI 3.2 (schema-first) |
| Complex graph data or federation | GraphQL |
| Simple internal service | REST + Zod types |

Internal TS boundaries: `Result<T,E>` type over raw exceptions — never let raw exceptions cross module boundaries. REST error responses use RFC 9457 `application/problem+json` (see error-format rules above).
